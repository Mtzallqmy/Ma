أنت فريق تقني وعلمي متعدد التخصصات يضم: Principal Android Architect، Kotlin/Jetpack Compose Engineer، Android 3D Rendering Engineer، Medical Anatomist، Clinical Pharmacist، Medical Content Reviewer، Neon/PostgreSQL Architect، Offline-first Engineer، UX/UI Specialist، Security Engineer، QA/CI Engineer.

تابع العمل مباشرة داخل مشروع «دواء وحياة» نفسه الذي أُنشئ في المرحلة الأولى في Google AI Studio. هذه هي المرحلة الثانية من الخطة المختصرة ذات خمس مراحل. المطلوب تحويل أقسام أجهزة الجسم والتشريح والأمراض إلى خصائص أصلية عاملة ومترابطة، وليس إنشاء خطة نظرية أو نموذج تصميم أو موقع إلكتروني جديد. افحص أولًا ما نُفذ في المرحلة الأولى، وثائقها، وبنيتها، وملفات Kotlin/Compose/Gradle/Room/API، ثم أضف ما ينقص دون نسف أي وظائف سابقة.

مهم جدًا بشأن بيئة Google AI Studio:
- المشروع المعتمد Android Native بكود Kotlin + Jetpack Compose وGradle، وليس React ولا PWA ولا Flutter ولا موقع ويب محوّل إلى تطبيق.
- إذا كانت البيئة الحالية توفر معاينة ويب فقط، احتفظ بمصدر Kotlin/Gradle قابلاً للتصدير في ZIP، ولا تعتبر المعاينة إثباتًا لتشغيل تطبيق Android أو تكامله. لا تُنشئ واجهة ويب بديلة بدعوى سهولة المعاينة.
- نفّذ واختبر بما تسمح به الأدوات الحقيقية. إذا تعذر تشغيل محاكي أو إجراء Gradle build داخل Google AI Studio، سجّل بوضوح «لم يُختبر محليًا» مع خطوات اختبار قابلة للتنفيذ عبر GitHub Actions/Android Studio. لا تدّع تشغيل اختبارات لم تُجرَ.
- لا تعاود كتابة المرحلة الأولى أو تبدّل قاعدة Neon أو تعيد تسمية التطبيق. لا تعمل في مشروع Flutter الأصلي أو مستودع آخر. استخدم المشروع التجريبي المنفصل لهذه النسخة فقط.
- إن توفرت صلاحيات GitHub متصلة ارفع التعديلات إلى فرع المرحلة الثانية وافتح PR وشغّل CI، وإلا جهّز ملف ZIP حقيقيًا قابلاً للتصدير مع ملفات المصدر وتقارير الاختبار، ولا تدّع حصول النشر.
- لا تنتج APK تجريبيًا للمستخدمين الآن. أول Beta مقرر بعد المرحلة الثالثة من هذه الخطة الخماسية، وأول إصدار مستقر بعد المرحلة الخامسة. يسمح بتجميع APK داخلي للاختبار من دون توزيعه.
- لا تبدأ المرحلة الثالثة إلا بأمر صريح من المالك.

1) المتطلبات غير القابلة للتغيير من المرحلة الأولى

المالك والمطور: الدكتور الصيدلاني معتز العلقمي — اليمن، تعز — 2026.

- الحد الأدنى Android 8.0 (API 26)، واستعداد لاحق لإنشاء Release APK بنظام ARM64-v8a 64-bit.
- Single Activity / Kotlin + Jetpack Compose + Material 3؛ نظام تنقل فعلي، وضع فاتح/داكن، خط عربي مريح، دعم RTL عربي وLTR إنجليزي والمصطلحات اللاتينية حيث تصح.
- Neon فقط: PostgreSQL للمحتوى المنظم والعلاقات والمراجع، Neon Object Storage للصور والمجسمات الثقيلة وحزم التحميل، Neon Functions لواجهات HTTPS API الآمنة. ممنوع Supabase وFirebase كبديل تلقائي.
- Room/SQLite داخل الهاتف للمعلومات الأساسية والفهارس ونسخ الحزم، وDataStore للإعدادات، وWorkManager للتنزيلات الاختيارية.
- قاعدة الاستخدام Local-first: افتح المحتوى الموجود في الجهاز فورًا؛ ما لم يُنزَّل يمكن عرضه عبر الإنترنت عند توفره؛ التنزيل بحسب القسم أو العضو أو الملف أو اللغة أو الجودة اختياري، ثم العمل بلا إنترنت بعد التثبيت الدائم.
- لا اتصال PostgreSQL مباشر من تطبيق Android؛ لا تضع DATABASE_URL ولا Neon secret keys ولا بيانات S3 في العميل. كل الوصول السحابي عبر API موثق وآمن.
- لا تمس البيانات والمفضلة والملاحظات والتنزيلات الموجودة عند إضافة المرحلة الثانية أو ترقية قاعدة Room.
- لا تنشر تشخيصًا أو خطة علاج فردية ولا جرعات دوائية غير مراجَعة. المعلومات التعليمية يجب أن تتضمن مصادرها وحالة مراجعتها وحدود استخدامها.
- حافظ على التنقل السفلي: الرئيسية، جسم الإنسان، الأمراض، الأدوية، مكتبتي. لا تكسر تبويبات المرحلة الأولى.

2) مسح المنجزات وتقرير الفجوات قبل التنفيذ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

نفّذ تدقيقًا فعليًا لكل مجلد وميزة من المرحلة الأولى: Room entities وDAO وmigrations وSeed، مصدر البيانات المحلي والسحابي، ContentPackManager، البحث، اللغة، downloads، شاشات الأجهزة/الأمراض، UI theme، 3D contract، CI والتوثيق. اعمل جدول Current / Missing / Planned Fix، لكن لا تتوقف عند التقرير؛ نفّذ الإصلاحات فورًا.

إن وُجدت وظائف غير مكتملة، أصلح الحد الأدنى الذي تعتمد عليه المرحلة الثانية؛ إذا كان عائق ربط Neon خارج أدوات Google AI Studio، نفّذ طبقة الربط والعقود والمخططات وملفات النشر الخارجية بوضوح، ثم اختبر التكامل الفعلي فقط إذا امتلكت الصلاحية والوصول.

3) موسوعة أجهزة جسم الإنسان — Human Body Systems
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

أنشئ قسمًا متكاملًا قابلًا للبحث والاستعراض يضم على الأقل نظام فهرسة صريحًا لأجهزة الجسم التالية، مع تجميعات علمية مناسبة دون تكرار مضلل:
- الجهاز العصبي Nervous System.
- القلب والأوعية الدموية Cardiovascular System.
- الجهاز التنفسي Respiratory System.
- الجهاز الهضمي Digestive System.
- الجهاز البولي/الكلوي Urinary/Renal System.
- الجهاز التناسلي Reproductive System.
- الغدد الصماء Endocrine System.
- الهيكل العظمي Skeletal System.
- الجهاز العضلي Muscular System.
- الجهاز المناعي واللمفاوي Immune/Lymphatic System.
- الجلد/الجهاز اللحافي Integumentary System.
- الحواس الخاصة Special Senses.
- الدم والجهاز المكوّن للدم Hematologic System عند مناسبة التصنيف.

لكل جهاز أنشئ صفحة شاملة منظمة:
1. الاسم العربي، الإنجليزي، والمصطلح اللاتيني التشريحي إن أمكن إثباته.
2. التعريف ووظيفته الأساسية وعلاقته ببقية الأجهزة.
3. خريطة الأعضاء والأقسام الفرعية مع انتقال فعلي إلى صفحة كل عضو.
4. شروحات Anatomy وPhysiology واضحة بعناوين وصور ومخططات مرخصة.
5. مجسم 3D أو صورة توضيحية مع بيان نوع الوسيط الحقيقي، وجودته، وحالة تنزيله.
6. الأمراض المرتبطة بالجهاز مع تصنيفها وأولوية التعلم، ولا تعرض أنها قائمة شاملة إذا لم تكن كذلك.
7. ارتباط الفئات الدوائية ذات الصلة عند وجود محتوى معتمد من مراحل المشروع.
8. المراجع وتاريخ تحديث المعلومات والرخصة وحالة المراجعة.
9. أزرار النسخ والمفضلة والمشاركة والحصول على الحزم المتاحة دون اتصال.
10. حالة «لا توجد نسخة 3D لهذا العضو بعد» عندما تكون صحيحة؛ لا تجعل كل الأجهزة تعرض النموذج نفسه على أنه نموذج علمي خاص بها.

لا يكفي إنشاء 13 بطاقة لا تفتح شيئًا. لتأكيد اكتمال المرحلة الثانية، أنشئ صفحات تعليمية مفصلة ومرتبطة فعليًا لمسار عينة علمية محترم على الأقل: الجهاز القلبي الوعائي (القلب/الأوعية)، الجهاز التنفسي (القصبة/الرئتان)، الجهاز الهضمي (المعدة/الكبد)، الجهاز البولي (الكليتان)، والجهاز العصبي (الدماغ/الأعصاب). بقية الأجهزة تحصل على بنية فهرسة، ومعلومات تأسيسية موثقة، وقوائم أعضاء بقدر ما يتوفر، دون فبركة شروحات غير مراجعة.

4) صفحات الأعضاء والبنية التشريحية الدقيقة
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

لكل عضو نموذج Entity ثابت مرتبط بجهاز أو أكثر باستخدام canonical identifiers، وليس أسماؤه الحرة فقط. تخطيط الصفحة:
- ملخص العضو، موقعه، أجزاؤه، أدواره الفسيولوجية، التروية الدموية/التعصيب حيث مناسب.
- صورة تشريحية عالية الوضوح ومصدرها، وملاحظات تظهر فوق الأجزاء عند الضغط.
- تسميات Arabic / English / Latin إن كان متاحًا، مع زر تغيير لغة التسميات مستقل عن لغة واجهة التطبيق.
- قابلية التنقل بين العضو والجزء والمرض والمصدر وحزمة المجسم.
- روابط بين أعضاء ذات علاقات تشريحية أو وظيفية مفهومة، دون حسابات سببية زائفة.
- عناصر التفاعل: تكبير الصورة، التحريك، بطاقات شرح، عرض/إخفاء التسميات، نسخ مصطلح، عرض المرجع.
- اظهر الاختلاف بين نموذج تشريحي مثبت علميًا، وصورة فنية تعليمية، ومجسم تجريبي تقني.

اقتراح هياكل Android/Neon الجديدة: anatomy_labels، anatomical_structures، anatomy_relationships، organ_sections، organ_diagrams، anatomy_3d_assets، model_structure_meshes، localized_terms، science_figures، figure_annotations، source_attributions. عدّل المخطط القائم بمهاجرات قابلة للتطبيق دون إنشاء نسخ مكررة من جدول العضو أو المصدر.

5) عارض التشريح ثلاثي الأبعاد الحقيقي — 3D Anatomy Viewer
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

هذه ميزة إلزامية ذات أولوية عالية. المطلوب مشهد 3D حقيقي لا صورة ثابتة بها زر 3D. اختر حلًا مستقرًا وقابلًا للبناء على Android 8:
- الخيار المفضل إن توفرت مكتبة متوافقة ويمكن اختبار Gradle: Google Filament مع تحميل GLB/glTF بصورة صحيحة.
- البديل المشروع: WebView مع عارض WebGL/Three.js مضمّن محليًا ومحزّمًا داخل التطبيق لصفحة عارض فقط، وليس واجهة التطبيق كلها؛ يجب أن يعمل دون CDN أو خدمات سحابية إذا كانت ملفات 3D محلية، مع حماية روابط WebView والتعامل مع عزل الملفات.
- قبل اعتماد محرك، تحقق من ترخيص المكتبة والتوافق/الحجم والذاكرة وAPI 26 و64-bit، ولا تدّع أن مكتبة Android Native متاحة في بيئة المعاينة إذا تعذر بناؤها.

وظائف العارض المطلوبة بنسخته الثانية:
- عرض مجسم GLB واحد على الأقل لعضو/بنية تشريحية مرخّصة بالفعل، مع تدوير حر، تكبير/تصغير، تحريك مناسب، إعادة وضع الكاميرا، مؤشرات التحميل، ورسالة خطأ حقيقية.
- اختيار جزء محدد بالضغط (mesh picking/raycast أو تعريف أجزاء أخرى موثق)، إبرازه وربط تسميته بالشرح. إن كان النموذج غير مقسّم إلى meshes معرّفة، لا تزعم أن اختيار الأجزاء فعال.
- إظهار/إخفاء البنى والطبقات عند توفر نموذج متعدد الطبقات؛ شفافية وعزل العضو إن سمح أصل المجسم، مع إبقاء الميزات غير المتاحة معطلة بصراحة.
- تفاصيل الجزء المختار تعرض الاسم بالعربية والإنجليزية واللاتينية عند وجوده، والوظيفة والمصدر.
- شاشة واسعة Fullscreen مع وضعين فاتح/داكن، تعليمات تعامل أول مرة، زر إعادة ضبط.
- دعم thumbnail/image fallback إذا فشل WebGL/GPU أو تجاوزت الذاكرة حدود الجهاز.
- إحصاء زمن فتح المجسم وحجم الملف وذروة الذاكرة في بيئة الاختبار المتاحة.

التعامل مع الملفات:
- أسماء الملفات والمسارات آمنة، وعرض من URI محلي مثبت أو HTTPS موثوق.
- بدائل جودة Low/Medium/High كأصول مستقلة LOD عند توافرها؛ لا تنزل High تلقائيًا.
- ضغط GLB بطرق مدعومة في العارض، وتجنب نموذج يتسبب في نفاد RAM على هواتف متوسطة.
- لا تتطلب اتصال إنترنت لعرض 3D الذي نزله المستخدم واكتمل تثبيته.
- إجراء fallback في حال غياب العتاد/المكتبة أو فشل Shader بدل شاشة سوداء أو انهيار.

الأصول القانونية:
- راجع BodyParts3D (https://dbarchive.biosciencedbc.jp/en/bodyparts3d/)، Z-Anatomy (https://github.com/Z-Anatomy/Models-of-human-anatomy)، وOpen Anatomy Atlas (https://github.com/CognitionLabSNUC/open-anatomy-atlas) أو أصولًا أخرى موثقة، وتحقق من ترخيص كل ملف/نسخة/عنصر، لا من اسم المشروع فقط.
- يُمنع سحب صور من Google Images أو نسخ مجسمات تجارية أو محتوى يحمل شرط NC غير متوافق أو اشتراطات أخرى دون تحليل مكتوب للترخيص ومصدر الأصل ونسبته.
- إذا لم تتوفر أصول صالحة لإعادة التوزيع، استخدم نموذجًا هندسيًا موسومًا «فحص تقني فقط» لإثبات التدوير والتحميل، ولا تصفه بأنه عضو تشريحي معتمد. هذه الحالة لا تغلق شرط وجود أصل تشريحي صحيح.

حوّل تبويب «الأمراض» إلى موسوعة منظمة ترتبط بـBodySystem وOrgan وAnatomicalStructure بمعرّفات مستقرة. أنشئ صفحات عناوين وأبحاث مرضية ابتدائية حقيقية تركز على أمراض شائعة متعددة الأنظمة مثل:
- ارتفاع ضغط الدم، مرض الشريان التاجي، قصور القلب.
- الربو، داء الانسداد الرئوي المزمن، الالتهاب الرئوي.
- الارتجاع المعدي المريئي، قرحة المعدة/الاثني عشر، التهاب الكبد الفيروسي (بوصف طبي موثّق).
- داء السكري، قصور الدرقية وفرط الدرقية.
- إصابات الكلى الحادة، المرض الكلوي المزمن، التهاب المسالك البولية.
- الصرع، السكتة الدماغية، الصداع النصفي.
- فقر الدم بعوز الحديد، التهاب المفاصل أو هشاشة العظام، والأمراض الجلدية التعليمية الشائعة.

لكل مرض، هيكل صفحة ثابت (لا تعرض كل الحقول كحقائق إذا لم تُوثّق):
A) نظرة عامة وتعريف، الأجهزة/الأعضاء المتأثرة.
B) Epidemiology / عوامل الخطورة عند وجود مصدر.
C) Pathophysiology: الآلية المرضية، مع رسم/مخطط وتعريف المصطلحات.
D) المظاهر والأعراض والعلامات، مع علامات الخطر والحالات التي تتطلب طوارئ وفق إرشاد موثق.
E) التشخيص: الفحوصات الأساسية، التقييم، والتشخيص التفريقي من المصادر السريرية المسموح باستخدامها.
F) العلاج غير الدوائي: نمط الحياة والتثقيف والوقاية والمتابعة ضمن مرجع مناسب.
G) العلاج الدوائي: الفئات العلاجية العامة وآلية الفكرة العلاجية وارتباط المادة الفعالة، ولا تضع جرعات أو تعديلات سريرية غير مراجَعة.
H) المتابعة والنتائج والمضاعفات والفئات الخاصة عند توفّر إرشادات موثقة.
I) مصادر موثوقة وتاريخ نشرها وتاريخ الاستيراد وتاريخ المراجعة البشرية إن حدثت.
J) مصطلحات عربية/إنجليزية وروابط للعضو و3D والمفضلة والنسخ والتنزيل.

أدخل فصلًا واضحًا بين «معلومات طبية تعليمية عامة» و«إرشادات سريرية مرجعية قد تتغير» و«معلومات جرعات/علاج حساسة تتطلب تحقق صيدلاني/طبي». تجنب إدخال بروتوكولات اعتمادًا على توليد لغوي وحده. لدى غياب مراجعة بشرية لجزء علاجي، اعرض بيانات علمية توضيحية محايدة ووسم under_review أو محجوبة عن النشر الطبي المعتمد؛ لا تضع وسم approved على المحتوى بناءً على تقدير النموذج.

يُفضل تنفيذ 15–20 صفحة مرضية أساسية ذات مقدمة علمية ومدخل موثق وحقول معلومات تمت مراجعة مرجعيتها قدر الممكن، وتظهر بوضوح درجات الاكتمال. لا تملأ حقولًا علاجية مزعومة لمجرد الوصول إلى العدد. يجب ألا يتسبب غياب شبكة في اختفاء مقالات الأمراض الأساسية المضمّنة في APK.

7) المراجع والإرشادات الطبية وآلية البيانات المعتمدة
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

استخدم مصادر فعّالة قانونيًا ومناسبة لنوع المحتوى، وتحقق من وثائق API/licensing والتواريخ قبل الاستيراد:
- MedlinePlus (https://medlineplus.gov/) لفهم المرض والتثقيف الصحي. راعِ أن أجزاء من المحتوى الدوائي قد تخضع لحقوق جهة أخرى.
- WHO (https://www.who.int/) للإرشادات والأمراض والأدوية الأساسية، عند سماح الترخيص.
- NICE (https://www.nice.org.uk/guidance) للإرشادات السريرية للاستشهاد/التلخيص الأصلي وفق شروط الاستخدام، دون نسخ مراجع محمية.
- WHO ICD-11 (https://icd.who.int/) لتصنيف الأمراض عند توفر حق/واجهة مناسبة، ولا تعرض التطابقات على أنها دقيقة دون معايرة.
- PubMed/NCBI E-utilities (https://www.ncbi.nlm.nih.gov/books/NBK25500/)، Europe PMC (https://europepmc.org/RestfulWebService) لفهرسة الدراسات وروابطها ومُلخصاتها بحسب الرخصة.
- Crossref (https://www.crossref.org/documentation/retrieve-metadata/rest-api/) وOpenAlex (https://docs.openalex.org/) للبيانات الوصفية والتتبع المرجعي.
- ClinicalTrials.gov API (https://clinicaltrials.gov/data-api/api) إن كانت معلومات التجارب ذات صلة بالمرض ومستوى الدليل؛ سجّل بوضوح الفرق بين بحث تجريبي وعلاج معتمد.
- OpenStax Anatomy & Physiology (https://openstax.org/) كمصدر مرجعي وفق شروطه الخاصة؛ لا تُدخل كتبًا أو صورًا محمية تلقائيًا.
- SNOMED CT/LOINC/UMLS: جهّز معرفات مناسبة فقط إذا كانت الشروط والتصاريح ملائمة، ولا تفترض مجانية إعادة التوزيع في اليمن أو لقاعدة البيانات الموزعة.

صمّم SourceRegistry وProvenance موحدًا من المرحلة الأولى يحفظ: source URL، DOI إن وجد، publisher، authors، publication date، retrieved_at، license، attribution، dataset/version، language، evidence_type، review_status، reviewed_at (فقط عند مراجعة بشرية حقيقية)، applicable_region. فرّق بين توصية جمعية/دليل سريري وبين مقال تثقيفي وورقة بحثية أولية.

أضف «عرض المصادر» إلى كل صفحة عضو أو مرض. عند تحديث مقال أو تغيّر إصدار دليل، احتفظ بالنسخ والمصدر السابق ولا تستبدل المعلومة محليًا بصمت.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
8) Neon: البيانات والحزم، والخادم دون أسرار في Android
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

احترم Neon باعتباره سحابة المشروع: Neon Postgres/Neon Object Storage/Neon Functions. إذا كان هناك مشروع Neon مخصص متصل في المرحلة الأولى، استخدم نفس project/branches وحدها وتجنب أي مشروع آخر؛ إذا لم يتوفر وصول صريح، لا تخلق نجاحًا وهميًا ولا تضف DATABASE_URL داخل التطبيق.

- أنشئ migration جديدة للجدوال والعلاقات التشريحية والأمراض، بمفاتيح وفهارس وقيود واضحة ومطابقة للـRoom Entity mapping. لا تمس الجداول المنشورة أو تحذف البيانات.
- ضع الـAPI خلف Neon Functions: GET /v1/body-systems، GET /v1/organs/{id}، GET /v1/anatomy/models?organId=...، GET /v1/diseases?systemId=...، GET /v1/diseases/{id}، GET /v1/content-packs?scopeType=...، GET /v1/packs/{id}/manifest، GET /v1/assets/{id}/access، GET /v1/sources/{id}.
- أسماء endpoints قابلة للتوفيق مع عقد المرحلة الأولى؛ لا تنشئ مسارين متضاربين لكل وظيفة. استخدم إصدار API وعقود DTO واختبارات contract.
- تأكد أن القراءات العامة تسمح فقط بالمقالات public/published والمراجعة/الترخيص المطلوبين، والمراجع العامة المسموح بها، مع limits وpagination وvalidation وETag.
- للأصول الخاصة استخدم روابط مؤقتة مع سياسات وصول مضبوطة؛ للأصول المرخصة للنشر العام يمكن استخدام public_read بحسب التوثيق وسياسة التخزين.
- الملفات الثنائية GLB والصور والأرشيفات في Neon Object Storage لا في أعمدة PostgreSQL. جداول metadata تشير إلى object keys وsha256 والأحجام وlicense وversion وLOD.
- تحقق من دعم المنطقة المختارة لتخزين Neon وFunctions وفق التوثيق الحالي؛ لا تستخدم منطقة ليس بها الخدمات ثم تعلن اكتمالها.
- اختبر عبر HTTPS إذا كانت بيئة نشر Neon متاحة. وإلا أنشئ دوال الخادم والـmigrations والعقود كملفات مشاريع منفصلة قابلة للنشر خارج Google AI Studio، ودوّن شرط «التكامل لم يُختبر».

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
9) التنزيلات الاختيارية Offline Packs لكل عنصر أو قسم
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

لا تعِد بناء محرك التنزيل من الصفر. وسّع ContentPackManager الموجود بالمرحلة الأولى بحيث يدير حزم التشريح والأمراض والصور و3D من نفس واجهة التنزيلات.

أمثلة حزم مستقلة قابلة للاختيار:
- cardiovascular-text-ar-v1 (نص الجهاز بالعربية).
- cardiovascular-figures-v1 (صور ورسومات).
- heart-model-low-v1 (مجسم القلب منخفض الجودة إن كان متوفرًا بترخيص صحيح).
- heart-model-high-v1 (جودة عالية منفصلة، لا تنزيل تلقائي).
- respiratory-diseases-ar-v1 (أمراض الجهاز التنفسي، بيانات معتمدة فقط).
- single-disease-[canonical-id]-ar-v1 (مقال واحد ومراجعه ومواده المرخصة).
- anatomical-terms-en-latin-v1 (مصطلحات اختيارية معجمية).
هذه أمثلة لمعرفات تصميمية وليست ادعاءً بوجود حزم منشورة مسبقًا.

في واجهة كل جهاز/عضو/مرض أظهر حالة: مضمن داخل التطبيق، متاح عبر الإنترنت، غير منزّل، منزّل، تنزيل جارٍ، تحديث متاح، خطأ. زر «التنزيل» لا ينزل جميع الصور والمجسمات للموسوعة بلا موافقة.

فصل الحزم النصية عن حزم الصور والمجسمات شرط إلزامي. معلومات حجم التحميل تشمل التبعيات قبل الموافقة. سجل محلي Room يربط packId/version/file hashes/installedAt/localPaths/source revisions، ويشغّل المعاينة من الملف المحلي بلا شبكة. لا تعتبر ملفات image cache العابرة حزمة Offline مكتملة.

اشتراطات سلامة: HTTPS، حجم وSHA-256 لكل ملف، staging ثم تثبيت ذري أو آمن، retry/backoff، مساحة حرة كافية، إلغاء حقيقي، الحفاظ على الإصدار القديم عند فشل التحديث، path traversal protections، عدم حذف المفضلة، حذف الحزمة نفسها باختيار المستخدم. استئناف البايتات فقط إذا يدعم الخادم HTTP Range، وإلا استئناف على مستوى الملف مع وصف صادق.

سيناريو اختبار إلزامي عند توفر الأصول:
1. تثبيت التطبيق وفصل الشبكة وفتح درس الجهاز الأساسي المدمج.
2. وصل الشبكة واستعراض نموذج/موضوع لم يُنزّل بعد وعرضه عبر API.
3. تنزيل مجسم واحد وصورة ونص لمرض معين مع تقدم حقيقي.
4. فصل الشبكة وفتح نفس العضو ومجسمه وصفحته المرضية دون استدعاء سحابي.
5. إغلاق التطبيق وفتحه من جديد بلا شبكة للتأكد من بقاء الملفات والـRoom index.
6. حذف الحزمة مع بقاء المحتوى المدمج والمفضلة؛ إعادة التحميل عند الاتصال.
7. تجربة فشل تنزيل/Checksum/انقطاع، والتحقق من أن المحتوى السابق لا يتلف.

10) تجربة المستخدم والتصميم التفصيلي
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

أكمل هوية المرحلة الأولى نفسها: #123F42، #238982، #DAB977، #F5F8F7، #24334B. الواجهة عربية RTL أصلًا، إنجليزية LTR، والمصطلحات الإنجليزية/اللاتينية تُعرض دون انقلاب حروف. اعتمد تصميمًا طبيًا فخمًا مع صور أصول موثقة، حواف متوازنة، تباين واضح، تنقل سلس، وعناوين مرئية مناسبة.

صمّم شاشات فعلية على Compose، وليس لقطات ثابتة:
- صفحة فهرس أجهزة الجسم مع فلاتر ومخطط بسيط وأيقونات مقننة.
- صفحة الجهاز وعرض أعضاء مع صورة/نموذج والروابط للأمراض.
- صفحة العضو ومكون قسم الصور/العارض 3D/التسميات والمراجع.
- صفحة 3D Viewer وحدها مع تحكمات تفاعلية.
- صفحة الأمراض مع بحث وتصنيف حسب جهاز الجسم.
- صفحة مرض بتبويبات: التعريف، الآلية المرضية، الأعراض، التشخيص، العلاج غير الدوائي، العلاج الدوائي العام، المصادر.
- لوحة «مصادر وأدلة» تعرض الترخيص وتاريخ الدليل ودرجة المراجعة.
- Modal أو Bottom Sheet للتنزيل حسب النصوص والصور والمجسمات والجودة مع أحجامها.
- واجهة إدارة تنزيلات وتحديثات للأقسام الفردية.

أزرار القراءة والنسخ والمشاركة والمفضلة والأزرار الراجعة والمصادر والبحث والتنزيل تعمل فعليًا؛ لا تضف شاشات شكلية. UX لحالات loading/error/no internet/no model/permission/source missing. لا تستخدم توليد تصميم يكتب مصطلحات عربية مشوهة. احترم قارئات الشاشة وحجم النص الكبير والهواتف الصغيرة.

11) معمارية Kotlin/Room المطلوبة
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

أكمل القاعدة القائمة دون تغيير معمارية المشروع، واجعل كل نوع محتوى منظّمًا في data/local، data/remote، repository، domain، Compose UI. أضف/وسّع:
- BodySystem, Organ, AnatomicalStructure, AnatomyLabel, Figure, Model3DAsset.
- Disease, DiseaseSystemLink, DiseaseOrganLink, DiseaseSection, DiseaseSourceLink.
- ContentItem, ContentTranslation, Source, ContentRevision, ReviewState.
- PackManifest, PackFile, DownloadJob, LocalAssetPath, InstallVersion.
- DAO / FTS and normalized Arabic/English query paths / migrations / tests.

لا تُبْقِ البيانات في قوائم Kotlin ثابتة غير قابلة للتحديث إذا كان المطلوب تحميلها وإدارتها. المكوّن الأساسي يبدأ من Room seed، والمحتوى الإضافي يُسترجع من repository محلي أولًا ثم عبر الـAPI بحسب الحالة والسياسة. احفظ فتح العضو/المرض الأخير، الفهرس، التقدم والمفضلة المحلية باستمرار. إذا كانت هناك كيانات مماثلة في المرحلة الأولى، وسّعها بدل إنشاء كيانات متنافسة.

12) الفحوص والتحقق العلمي والتقني
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

اجعل الاختبار جزءًا من العمل وليس طلبًا نظريًا. نفّذ ما يلي بحسب الإمكانيات، وسجل Passed / Failed / Blocked / Not run مع دليل لكل نتيجة:
- اختبار Kotlin/Gradle compilation، lint، Room schema/migrations، serialization/manifest.
- اختبار شاشة الأجهزة: قائمة + انتقال إلى عضو + فتح مقاطع ومصادر.
- اختبار شاشة الأمراض: ربط المرض بجهازين عند الحاجة، وعدم إنشاء معلومات بلا مصدر.
- اختبار البحث عربي/إنجليزي/مصطلحات لاتينية، تطبيع الهمزات واختلاف كتابة الأسماء دون تغيير النص المعروض.
- اختبار 3D: تحميل GLB صالح، تدوير، pinch-to-zoom، اختيار mesh معرف، reset، فشل الملف، ضعف GPU، العمل بلا شبكة.
- اختبار Neon API الحقيقي إذا كان منشورًا: catalog/system/organ/disease/asset/manifests، وعدم تسريب المسودات أو الأسرار.
